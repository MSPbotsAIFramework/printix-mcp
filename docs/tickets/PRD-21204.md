## Product design

### Goals / Non-goals

**Goals** (matches the one-line ask exactly):
- An agent can list and inspect a Printix tenant's printers/print queues.
- An agent can list and inspect a Printix tenant's sites.
- An agent can list and inspect a Printix tenant's workstations.
- Each of the above works for a tenant whose Printix admin has issued the Agent Platform an OAuth client_id/client_secret pair.

**Non-goals** (explicitly out of scope — no comment or description text asks for these, and adding them would be scope creep for a "look up X" ticket):
- Submitting, deleting, or otherwise mutating print jobs.
- Creating/deleting/updating users, groups, cards, networks, or SNMP configuration (the Cloud Print API exposes these; this ticket is read-only lookups).
- Any UI/console surface — this is an MCP connector with no agent-platform-side screen of its own; "product design" here means the tool contract an agent and its user interact with, not a page.

### Acceptance criteria AC1..AC10

These are the pass/fail statements; full Given/When/Then steps and evidence live in the sibling `PRD-21204.ac.json`.

- **AC1**: Listing a tenant's printers/queues returns the queues for that tenant (name, id, status, site), paginated, with a `has_more` flag when more exist than the page size.
- **AC2**: Looking up one printer/queue by id returns that queue's full properties/capabilities.
- **AC3**: Looking up a site or workstation id that does not exist returns a structured "not found" result, not a crash or an opaque 500.
- **AC4**: Calling any Printix tool without the required credential headers returns 401 with the list of required headers in the body — never a 500.
- **AC5**: Calling any Printix tool with a credential pair Printix itself rejects (bad client_id/secret) returns a structured "unauthorized" result from the tool, distinct from AC4's transport-level 401.
- **AC6**: When the caller's credential pair has access to exactly one Printix tenant and no tenant id header was supplied, the tool resolves that tenant automatically and proceeds.
- **AC7**: When the caller's credential pair has access to more than one Printix tenant and no tenant id header was supplied, the tool returns a structured "invalid argument" result asking for the tenant id, listing the tenant ids it found.
- **AC8**: A tenant with zero printers (or sites, or workstations) gets back an empty list, not an error.
- **AC9 (multi-tenant isolation)**: Two concurrent lookups using two different tenants' credentials each see only their own tenant's printers/sites/workstations — never a mix.
- **AC10 (health)**: `GET /health` returns 200 without needing any Printix credentials and without calling Printix at all.

## Tech design

### Conclusion

Build the first version of `printix-mcp` from scratch (SOP main line A — the repo is an empty scaffold): a Python 3.12 + `uv` + FastMCP service exposing 6 read-only tools over Streamable HTTP, exchanging an OAuth2 client-credentials header pair for a Printix access token on every call (no cross-request token caching, per the SOP's stateless/isolation rules), and mapping Printix's REST responses onto the organization's structured tool-result envelope. This is the only natural shape for a brand-new MCP in this org — there is no existing code in this repo to extend, and every sibling vendor MCP repo in `MSPbotsAIFramework` follows this same contract.

### Where the current implementation lives

Nowhere yet. `README.md:1-2` (worktree `dev/PRD-21204` @ `c799955`) is the entire repository. There is no prior Printix integration anywhere in `MSPbotsAIFramework` (confirmed by the repo search logged in the earlier `[BLOCKED]` comment on this ticket) or in any MSPbots-owned repo.

No alternative considered: every other vendor MCP in this org (e.g. the Node/Python services referenced throughout `vendor-mcp-development-sop.md`) is built to the same contract — Python 3.12 + `uv` + FastMCP, Streamable HTTP `/mcp` + `/health`, header-only credentials, stateless. Picking a different stack or transport for this one repo would make it the odd one out with no corresponding benefit. The open-source `WYRE-AI/printix-mcp` is read only for "what capabilities exist," not forked or ported (SOP rule 3) — this repo is implemented clean-room against `printix.github.io`.

### Data & API contract

**Credential headers** (read by `auth_middleware.py`, declared in the README table):

| Header | Required | Meaning |
|---|---|---|
| `X-Printix-Client-Id` | yes | OAuth2 client id, issued per Printix tenant from the Administrator dashboard |
| `X-Printix-Client-Secret` | yes | OAuth2 client secret paired with the above |
| `X-Printix-Tenant-Id` | no | Printix tenant id to operate on; required only when the credential pair can see more than one tenant (AC6/AC7) |

**Tools** (all read-only; `readOnlyHint: true`, no `destructiveHint`):

| Tool | Params | Returns |
|---|---|---|
| `printix_list_printers` | `limit` (default 50, max 200), `cursor` (optional) | list of `{id, name, status, site_id}` + `has_more` |
| `printix_get_printer` | `printer_id` (required) | full printer/queue properties and capabilities |
| `printix_list_sites` | `limit`, `cursor` | list of `{id, name, address}` + `has_more` |
| `printix_get_site` | `site_id` (required) | full site details |
| `printix_list_workstations` | `limit`, `cursor` | list of `{id, name, site_id, last_seen}` + `has_more` |
| `printix_get_workstation` | `workstation_id` (required) | full workstation details |

Exact Printix-side pagination parameter names and field lists are taken from the live `https://printix.github.io/` reference at implementation time (Open question, non-blocking); the shape above (`limit`/`cursor`, `has_more`) is this service's own response contract, independent of whatever Printix calls its paging parameters internally — the client layer (`printix_client.py`) is the translation point.

**Error envelope** (tool-level, per SOP §4 — never an exception, never HTTP 500 from inside a tool call):

```json
{"error": {"code": "not_found", "message": "Printer 'abc123' was not found in this tenant.", "retryable": false}}
```

Codes used: `unauthorized` (Printix rejected the credentials — AC5), `not_found` (AC3), `invalid_argument` (ambiguous tenant — AC7; also malformed ids), `rate_limited` (AC-adjacent, §7), `upstream_error` (Printix 5xx or network failure after retries exhausted).

**Missing-header 401** (transport-level, before any tool runs — AC4):

```json
{"error": "missing_required_headers", "required": ["X-Printix-Client-Id", "X-Printix-Client-Secret"]}
```

**Backward compatibility**: not applicable — first version of a brand-new service, no existing clients to break.

### Key flow / sequence

```
Agent -> Gateway -> printix-mcp /mcp (tools/call printix_list_printers)
  printix-mcp:
    1. auth_middleware reads X-Printix-* headers -> contextvar (401 if required headers missing)
    2. printix_client: POST https://auth.printix.net/oauth/token (client_credentials) -> access_token
    3. if no X-Printix-Tenant-Id: GET https://api.printix.net/cloudprint -> tenant list
         - exactly one tenant -> use it
         - more than one -> return invalid_argument (AC7), stop
    4. GET https://api.printix.net/cloudprint/tenants/{tenantId}/printers?... -> map to tool response
    5. contextvar reset in `finally` regardless of outcome
  printix-mcp -> Gateway -> Agent: tool result (data or structured error)
```

### Non-functional

- **Idempotency & concurrency**: all 6 tools are GET-only against Printix; no write path exists, so there is no idempotency concern. Concurrent calls from different tenants are isolated purely by the per-request contextvar (no shared cache, no shared client state) — this is also the mechanism behind AC9.
- **Performance**: Printix tenant fleets (printers/sites/workstations) are small (MSP scale, not consumer scale); `limit` defaults to 50, hard-capped at 200, never unbounded. `httpx` timeouts: 5s connect / 30s read. 429/5xx get limited retries with backoff honoring `Retry-After`; total call budget per tool invocation stays under 120s including the token fetch.
- **Security**: credentials live only in the per-request contextvar, never logged, never written to disk or env; the OAuth token obtained in step 2 of the sequence above is used once and discarded — not cached across requests (SOP §3.4 forbids caching derived tokens in a shared-container, multi-tenant service). All calls to Printix are TLS.
- **Multi-tenant isolation**: tenant scope comes only from the current request's own credentials/header (resolved fresh each call, §"Key flow"), never from any state left by a previous request — this is architectural, not a runtime check, because there is nothing to leak from (contextvar is reset in `finally`, no cache keyed by tenant).
- **Observability**: log tool name, Printix HTTP status class, and the mapped error `code` (never request/response bodies, never credential header values) per call, so a failure can be triaged without the log itself becoming a secrets store.

## Decisions made by DEV01

(No one was available to ask; these are the first-version calls, each reversible by a future ticket.)

1. **Scope = read-only printers/queues, sites, workstations only**, excluding print-job submission and user/group/card/network/SNMP administration even though Printix's API offers them. Why: the ticket's one line is "Look up ... printers, queues, sites, and workstations" — an enumeration of read lookups, not a request for fleet administration or print-job control. Alternative not chosen: implement the full API surface up front — rejected as unrequested scope and unnecessary destructive-action risk (job submission, user deletion) for a ticket that asked only to look things up.
2. **Credentials = `X-Printix-Client-Id` + `X-Printix-Client-Secret`** (the OAuth2 client-credentials pair from the Printix Administrator dashboard), exchanged for an access token on every call. Alternative not chosen: accept a single pre-minted bearer token header — rejected because Printix access tokens expire in ~3599s and this service is stateless (no refresh-token storage across requests), so holding only a short-lived token would make the connector fail silently an hour after setup; the client-credentials pair does not expire the same way.
3. **Tenant id is optional**, auto-resolved when the credential pair sees exactly one tenant; required (with a clear error) when it sees more than one. Alternative not chosen: always require `X-Printix-Tenant-Id` — rejected because the common case (one Printix tenant per client-credentials pair, matching one MSP customer) shouldn't need an extra header; the ambiguous case still gets a clear, actionable error instead of silently guessing.
4. **No token caching across requests** — a fresh Printix OAuth token is fetched on every tool call. Alternative not chosen: an in-process cache keyed by client_id, refreshed near expiry — rejected because `vendor-mcp-development-sop.md` §3.4 explicitly forbids caching a derived token across requests in a shared, multi-tenant container; the extra round-trip per call is the accepted cost of that isolation guarantee, not a bug.
5. **Six named tools** (list+get pairs per resource family) rather than one generic query tool or more granular per-field tools. Alternative not chosen: a single `printix_query(resource_type, ...)` tool — rejected because named, typed tools are easier for an agent to select correctly and match every other MCP repo's convention in this organization (`<vendor>_<verb>_<resource>`).

### Changed fields vs. the posted tech design (not an AC change)

While wiring `printix_client.py` against the live `https://printix.github.io/` reference (exactly what the design's own Open Questions said the dev leg would do), three field names in the Tech design's "Data & API contract" table turned out not to exist in Printix's actual API responses. These are Tech design corrections (dev's own territory per this pipeline's rules — Tech design states *how*, not *what*; none of them touch the Acceptance Criteria's user-visible promises), not changes to any AC or test case:

| Design said | Printix actually returns | Where checked | Fix |
|---|---|---|---|
| `printix_list_printers`/`printix_get_printer`: `site_id` | No site reference at all on a print queue — only a free-text `location` field (e.g. `"Office"`), set by the tenant admin, not a foreign key | "Get printer properties" and "List Print Queues" response field tables, https://printix.github.io/ | Return `location` instead. AC1's parenthetical "(name, id, status, site)" is satisfied with the best real field that indicates where a queue sits |
| `printix_list_sites`: `{id, name, address}` | No `id` field at all per list item (only via `_links.self.href`'s last path segment) and no `address` field (Printix calls it `path`, a hierarchical location string, not a street address) | "Query Sites" response field table | `id` is derived from the HATEOAS self-link (see `_id_from_self_link` in `printix_client.py`); `address` renamed to `path`. No AC names an `address` field, so this is a pure data-contract fix |
| `printix_list_workstations`/`printix_get_workstation`: `site_id`, `last_seen` | No site reference on a workstation at all; Printix returns `active` plus two separate timestamps, `lastConnectTime` and `lastDisconnectTime`, not one `last_seen` | "Retrieve Workstation" / "Query Workstations" response field tables | Return `active`, `last_connect_time`, `last_disconnect_time`; dropped the non-existent `site_id` |

Also discovered and worth recording (no code impact, a credential-provisioning note added to the README instead): Printix's docs show `List Print Queues`/`Get printer properties`/site endpoints authorized under a "Cloud Print API application" while `Retrieve Workstation`/`Query Workstations` are authorized under a separate "Workstation monitoring application". If a tenant's admin issues only a Cloud Print API-scoped credential pair, the workstation tools will correctly surface as a structured `unauthorized` result (AC5, tested above) rather than succeed — this is expected vendor behavior, not a bug in this service, and is called out in the README's "Getting credentials" section so a connecting admin knows to grant the right application scope if they need the workstation tools.

### Self-chosen implementation details (beyond the design's own "Decisions made by DEV01")

- `get_printer`'s id-not-constructible-from-one-id situation (above) is handled by scanning the print-queue list, page by page (`pageSize=200`, capped at 50 pages = 10,000 queues), rather than guessing at Printix's two-segment path. Bounded and cheap for the MSP-scale fleets the tech design's Non-functional section already assumed.
- Token-bucket 429 and 5xx responses get up to 2 extra attempts with `Retry-After`-aware backoff (SOP §5); all other 4xx codes are not retried.
- `mcp[cli]` is pinned to `<2.0.0`: the SDK's 2.x line renamed `FastMCP` to `MCPServer` with a different constructor (no `stateless_http`/`transport_security` kwargs in the form this org's contract and this repo's own `TransportSecuritySettings`/`stateless_http=True` wiring assume). Every sibling MCP in this org is built against the 1.x `FastMCP` API per the tech design's Option analysis, so this repo matches that rather than adopting an unreviewed, differently-shaped 2.x API on its own.
